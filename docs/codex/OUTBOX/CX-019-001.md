## Delivered

`rust/rpp-link-udp` is always std-only and forbids unsafe code. It implements
the existing `LinkAdapter`, uses synchronous `UdpSocket`, and adds zero external
dependencies (only existing workspace path crates). Both config addresses and
Lan/Wifi/Internet kind are checked before socket creation; fields are private.
Loopback and the two card-specified tailnet ranges are allowed. Plain LAN,
public/wildcard/mapped addresses and BLE/LoRa kinds are refused. The address
check is a heuristic, **not proof of encryption, Tailscale presence or trust**.
Plain-LAN UDP still needs RADIX and is not implemented.

The [crate README](../../../rust/rpp-link-udp/README.md) specifies the informative
version/class prefix and limitations. Whole datagrams are capped at 1200 bytes,
including two prefix bytes (data payload 1198). Control is the existing codec's
112-byte envelope; probes/replies are 10 bytes. Source filtering uses the exact
IP AND port before any parsing or echo, including oversized foreign packets.
Only caller-verifier-approved `rpp_control::decode` results become control.
Sequence freshness remains host policy; no control kind, key or cipher was added.

Readings measure actual round-trip host elapsed time, not one-way latency. A
32-attempt rolling window records loss; Q4 integer RFC 3550 smoothing measures
successive RTT variation. ConnectionReset resolves the pending probe as loss,
never an error. Echo is BFD-inspired, not a BFD implementation: checked u64
counters, same-size replies, no repeated nonce replies, 32 replies/second, and
no third-source reflection. Data is one datagram, with no stream or retransmit.

The default live demo uses two actual loopback endpoint pairs, prints measured
readings, closes whichever peer fleet selected, records 32 failed probes, then
passes the readings to the unchanged resolver. The same flow test checks only
endpoint selection, availability, loss 1,000,000 and one total two-second bound;
no latency threshold. The observed final-source test passed in 0.60 s. The
example exited 0: initial RTTs 0/4 ms, both available; after closure endpoint1
had loss1,000,000/unavailable and fleet selected available endpoint2. These are
observations, not golden timings. Kind labels and prior signature/tunnel,
membership and consent inputs are fixtures; loopback proves no encryption.

## Choices and receive proposal

IMPOSED: the 1200 cap includes framing; pre-32 loss uses the actual sample count;
no samples means unavailable/loss1,000,000; latest probe determines availability;
first successful RTT seeds zero jitter; timeout is 1..250 ms; read drains at most
32 packets and retains at most four opaque app packets (overflow counted).
Idle resets increment a counter without inventing probes. Counter exhaustion
refuses rather than wraps. Replies have one attempt per increasing nonce.

Choose explicit `--exclude rpp-link-udp` for both riscv32 builds. Disabling
`fleet-demo` removes the optional example integration, not UDP's std requirement.
Existing heap-free crates continue compiling; this crate is not ESP32 firmware.
The Ubuntu/Windows job includes real loopback tests and the live example.

Proposed only, for TR/PL: a synchronous `ReceiveAdapter: LinkAdapter` method
`receive_into<'a, V: Verifier>(&mut self, scratch: &'a mut [u8], recipient: &NodeId,
verifier: &V) -> Result<Option<Inbound<'a>>, Self::Error>`, where `Inbound` is
borrowed data or an owned `VerifiedControlFrame`. Decide buffer-too-small,
backpressure, object-safety and verifier ownership before adoption. The current
method is adapter-local; no existing public trait was changed.
