## Scope and interpretation

Two new unpublished library crates prepare interfaces for future ESP32 adapters.
They implement no radio, vendor HAL, network, signing, cryptography, key storage,
identity provisioning, membership admission or consent mechanism. There is no
firmware binary or physical-board claim. Published specification, application
Python, layouts, consent header, golden vectors, constants and prior outboxes
remain unchanged.

IMPOSED: the control codec's fixed frame is an experimental internal format,
not an adopted RPP wire format. Its numeric tags, 112-byte length, 16-byte
identity fields and 64-byte opaque signature are provisional implementation
choices. No payload, text, TLV or extension field exists. The six closed kinds
are ALIVE, MEMBER-CHANGED, STOP, PAUSE, ROUTE-AROUND and RESUME. Decoding rejects
unknown kinds and extra bytes, including appended START, grants, consent, keys,
models and prompt/answer text. It does not scan opaque identity/signature bytes
for accidental ASCII words: those bytes never dispatch commands or payloads.

A caller-supplied verifier checks the exact header and opaque signature; no
accept-all production verifier, signing or cryptographic primitive is supplied.
Verification does not grant authority: membership, consent, command authority,
replay tracking, independent verified paths and trust remain host/policy duties.
A caller also supplies the expected recipient, binding the checked envelope to
its intended destination. All signature fixtures are explicit test assumptions.

## Adapter obligations and missing board information

An adapter must provide bounded link readings and separate control/data sends,
map caller identities, handle real transport framing/MTU/backpressure, report
failures, supply monotonic observation times, and pass externally verified
identity/tunnel/consent information to policy. It must preserve retry-before-first-
token, complete meter rows, control independence and billboard expiry. The
`rpp-control` verifier must be supplied by an existing reviewed protocol/backend;
this work selects or implements no cryptographic algorithm.

RADIX must supply the actual board models and deployment constraints before
hardware integration: chip/ISA (RISC-V versus Xtensa), RAM/flash budgets,
allocator strategy, radio availability/coexistence, BLE/GATT and LoRa MTUs,
power/sleep/timer behavior, firmware/toolchain/HAL versions and identity/verifier
backend. RISC-V library cross-builds do not certify a particular C3/C6 board.
Xtensa firmware and transport testing await that information.
