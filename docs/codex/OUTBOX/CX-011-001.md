## Bounds and preserved policy

The limits in `rust/rpp-fleet/src/limits.rs` are IMPOSED implementation choices,
not wire, address-layout or published specification constants. A small local
16-node registry with four alternatives per node is useful for initial ESP32
integration. Its maximum URI payload is `16 * 4 * 192 = 12,288` bytes.
This is not total heap use: caller-owned vector capacities, allocator and
container overhead, endpoints, stack and policy storage are additional. Board
models and an actual firmware allocator remain unknown; no physical memory-fit
claim is made.

The fleet constructor filters membership and consent inputs to registered IDs
and deduplicates before allocating policy labels: at most 16 members and 256
ordered consent pairs. The 40,000-input constructor regression covers duplicate
and unknown entries. Filtering does not grant membership or consent.

The fleet growth regression changes live readings and performs 10,000 data
and control resolutions. At that 10,000-operation checkpoint, retained counts
are 16 meter rows, one known data reference and one current data reference.
Returned global row IDs run
from 1 through 10,000; the retained window contains 9,985 through 10,000.
The core regression independently exercises 10,000 accepted controls after
bounded retention. These are retained-state counts, not allocator telemetry
or a claim that every transient allocation has constant size.

`preview_data` and `preview_control` are immutable queries over the same core
guards and ranking used by sends. They consume no clock, sequence, row, request
or known-reference state. At most four endpoint candidates are considered per
registered node. `choose_latest` replaces only the same endpoint pair's known
path after successful selection; unavailable/invalid selections preserve the
previous successful historical failure-domain reference. There is no new
reference TTL. This preserves independent STOP/PAUSE selection during a data
outage. Freshness, verified tunnels, consent, membership, replay, independent
failure domains, breakers, retry-before-first-token and routing weights stay
in the existing core policy. Ordinary core `choose`/send history is unchanged.

Every returned `ControlResolution`, including denied/no-channel outcomes,
contains its actual meter row. The internal 16-row buffer is diagnostic,
not a full historical ledger. Input errors need caller accounting; an error
does not promise a returned row. Hosts must retain returned rows externally
when they need complete history. Data resolution remains a query rather than
an actual metered send; rollback compares against accepted core control state,
not a separate monotonic history of every data-query tick.

The fleet rejects `u64::MAX` latency/jitter as invalid host-input sentinels and
loss above 1,000,000 ppm. Core `LinkReading::valid()` and score weights are
unchanged. URI validation is bounded shape validation, not a DNS or complete
URI parser. BLE/LoRa colon tails remain opaque metadata. A URI, address or
endpoint capability asserts no authorization, tunnel, device ownership or
physical path independence by itself.

+### 11.4 Informative Proposal: Fleet Assignment and Endpoint Records
+
+**Status: Proposed/informative, not an adopted specification contract.**
+This section describes the experimental `rpp-fleet` caller-assignment profile.
+It changes no canonical address layout, consent header, published constant,
+identity scheme or current resolver implementation.
+
+The canonical address specification defines fields and encoding, but neither
+it nor this resolver defines a derivation from an opaque lender/device identity
+to a canonical address. The separate `NETWORK.md` NodeRecord identifier,
+`SHA-256(public_key)`, is not such a derivation. No new hashing, truncation,
+key derivation or cryptographic ownership proof is proposed here.
+
+The named mode `explicit-caller-assignment-v1` requires the caller to supply an
+AddressBinding between an exact opaque identity and an existing canonical
+address. The experimental identity is the full pair of a 16-byte lender-key
+identifier and a 16-byte device identifier; these are identifiers, not keys.
+The existing 16-byte device identifier is also the explicit control-frame ID.
+These sizes are local implementation choices, not new published RPP fields.
+There is no default assignment mode. lookup_binding is a binding lookup: it
+returns the explicitly supplied address only for the matching identity.
+No address is computed from identity; a missing binding is Unassigned.
+The same identity and owner binding produce the same encoded address bytes;
+changing endpoint readings does not reassign the address.
+This is registry configuration, not permanent object identity or a future
+validity/consent promise. Hosts still resolve at point of access and enforce
+current policy; the semantic layer's temporal address rules are unchanged.
+
+A fleet registry checks unique full identities, encoded address words and
+control/device IDs within that registry. Machine registration uses the existing
+core canonical is_valid predicate, without another range table or reserved-bit
+filter. Binding objects can preserve other core-accepted states; registration
+does not admit those states as machine addresses. Duplicate/remap rejection
+leaves the registry unchanged. Local uniqueness does not make a 32-bit address
+globally unique, prove ownership, establish routability, grant membership or
+supply consent. Reassignment and ownership-transfer lifecycle are separate work.
+
+An endpoint record contains an endpoint ID, kind, URI, last LinkReading and
+capabilities. Endpoint IDs are u32 values unique within each node. Core link
+names use nAAAAAAAA-epEEEEEEEE: the registered encoded address word and endpoint
+ID as eight hexadecimal digits each. This reversible 20-character name is not
+a hash or truncated identity. Registry word uniqueness prevents link-name aliases
+inside the fleet, without asserting global address uniqueness. A resolver
+exclusively borrows its registry for its lifetime; structural bindings/endpoints
+cannot be replaced during that context, and only validated reading updates are
+forwarded. Proposed kinds are LAN, Wi-Fi, internet, BLE, LoRa and a
+WebSocketGateway profile. LinkReading carries integer latency/jitter in
+milliseconds, loss in parts per million, availability and observation tick.
+Capabilities are caller-supplied prior outcomes: tunnel_verified,
+reviewed_adapter, observation_verified and control_capable booleans plus a
+failure_domain identifier. They implement no authentication or device probing.

+is not evidence of independence. Additional record IDs and flags are metadata,
+not bits added to an RPP address or consent header.

+locality, reachability, encryption, authentication or device compatibility.

+with a nonempty host and no userinfo. Network-kind port shape and the gateway
